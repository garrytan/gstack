# Idea 003: What Agents Actually Are (And How They Get Built)

## Raw Dump
An agent in the Action Engine is not a chatbot. It is a task-specific execution unit: receives a classified request from the AI Orchestrator, pulls relevant data from the Semantic Layer or knowledge base, completes a task or delivers a data-backed answer, logs every action for auditability.

Agents are organized by capability pattern, not by business domain. A sales reporting question and a labor cost question may both be handled by the same agent type if they follow the same query pattern. Business domain specialization happens at the use case level, not the agent level.

Three agent types today:
KPI Agent: natural language to structured BigQuery query. Deterministic. High-frequency bulk of merchant interactions.
Complex Query Agent: multi-table joins, correlation, sophisticated SQL. The "why" questions.
RAG Agent: retrieves from product docs/knowledge bases via Vertex AI. Support, how-to, feature questions.

Future: Action Agents. Post-Alpha. Executes tasks on behalf of merchant (menus, scheduling, campaigns) with approval workflows. This is where platform moves from insight to execution.

How agents get built: use case validation (registry, agent type mapping, named semantic layer partner) → golden set creation (~50 real merchant questions with expected answers from support logs/SMEs) → data pipeline confirmation (DLAK Bronze→Silver→Gold→BigQuery) → agent development (orchestrator integration, domain-scoped access, logging) → accuracy evaluation (13-category framework, P0 = launch gates, P1/P2 iterative) → governance review (TAC/Risk Review Wave #224847, subsequent agents reference initial approval) → production deployment (monitoring, guardrails, fallback, switch-off capability required).

## Essence
Agents are capability-pattern units, not domain units. Three types today handle the spectrum from deterministic lookup to RAG retrieval. A rigorous 7-step build process — anchored by a ~50-question golden set and a 13-category eval framework — governs every agent regardless of who builds it. Action Agents (Phase 2) are where this moves from telling merchants things to doing things for merchants.

## Interesting Because
Organized by capability pattern, not business domain — genuinely non-obvious. It means the agent count stays small and reusable while the use case count can grow independently. That is leverage.

The golden set as accuracy benchmark is sharp. It is not vibes-based quality. It is 50 real merchant questions sourced from actual support logs. That is the difference between "we think it's accurate" and "we can prove it."

Switch-off capability required before any agent goes live. That sentence is doing a lot of work.

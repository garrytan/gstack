# Idea 004: Full PRD — Action Engine

## Raw Dump

### Problem
SMBs use 4.8 disconnected tools on average. Data gets surfaced but merchants still have to log in, interpret, decide, and manually execute. 36% of SMB owner work week is admin. Merchants without dedicated finance/ops/marketing staff feel this most.

Across GPN, product teams building AI independently = duplicated work, inconsistent merchant experiences, no unified governance. Each team reinvents agent infrastructure.

Market: 88% of US SMBs already using AI tools. 30% report unmet needs beyond current capabilities. 52% of European SME leaders accelerating AI adoption due to economic uncertainty.

### Goals
G1: Validate agents complete real merchant tasks end-to-end with acceptable accuracy
G2: Prove shared backend architecture works across at least one vertical
G3: Establish clear team boundaries between DLAK (data) and Action Engine (intelligence)
G4: Define and enforce governance, trust, and approval workflows for autonomous agent actions
G5: Build reusable infrastructure other GPN product teams can adopt without rebuilding

Non-Goals: No standalone consumer AI product. No full multi-vertical support in first deployment. Not replacing existing merchant tools. Not owning frontend chat long-term. No international launch beyond North America (but architecture should not block it).

### Users
Owner-Operators: time-constrained, wear multiple hats — need tasks completed, not just flagged
Store Managers: daily ops focus — need actionable direction and execution support
Finance/Ops Staff: domain specialists — need domain-specific agents that understand their function
DLAK Team: clear API contracts, stable schemas, defined SLAs
Product Teams (adopters): documented platform, clear onboarding, predictable APIs
Executive Leadership: visible progress, clear metrics, defensible competitive positioning

Initial Market: North America (minus Quebec). SMBs using Global Payments merchant services. First vertical: Restaurant via Genius.

### Functional Requirements (highlights)
P0: Orchestrator classifies intent and routes to appropriate agent
P0: Multi-agent handoff within single conversation
P0: Full audit log of every routing decision and agent invocation
P0: Each agent has defined scope, data access permissions, action boundaries
P0: Agents read from semantic layer or parameterized table functions
P0: MCP Server enables secure read/write across GPN systems [Needs Decision: implementation]
P0: Bronze→Silver→Gold data flow before reaching agents
P0: No autonomous financial transactions — explicit merchant approval required
P0: Complete audit trail of all agent actions and data accessed
P0: Short-term memory persists within session; memory scoped per merchant, no cross-merchant leakage
P0: Backend platform-agnostic, deployable to any interface via standard API
P1: Agents explain reasoning and data sources
P1: Long-term memory via vector store across sessions
P1: Merchant-facing transparency — disclose AI-driven actions and data accessed
P2: Proactive notifications without merchant needing to ask
P2: External data integration (Google Maps, Trends) for market context

### Non-Functional Requirements
Response time: <3 seconds standard, <30 seconds complex tasks
Scalability: 10,000+ concurrent merchant sessions
Uptime: 99.9% with graceful degradation
Security: PCI-DSS, SOC 2 Type II, encryption at rest and in transit
Extensibility: plugin architecture for new agents without platform changes
Data isolation: complete tenant isolation, no cross-merchant access

### Success Metrics
Alpha: Task completion rate 75%. Agent accuracy 85% weighted. Financial accuracy 95%+ (launch gate).
Beta: 250 active SMBs. NPS +50. 60% reduction in admin time [Gap: methodology undefined]. 80% using 2+ agent types monthly.
Scale: 10,000+ active merchants. 3+ internal GPN teams on platform. Revenue TBD [Gap: pricing undefined].

Measurement gaps that need resolution:
- Time saved methodology (needed before Beta)
- Task completion definition per task type (needed before Alpha)
- Revenue attribution methodology (needed before Beta)
- Pricing model (needed before Beta)
- Automated evaluation pipeline to replace manual testing (needed before production)

### Dependencies
D1: Open Lakehouse Bronze/Silver/Gold — DLAK — critical path for every team
D2: Semantic Layer — DLAK — coverage expanding
D3: AI Gateway (Apigee) — Action Engine — validated in Alpha
D4: GCP (Vertex AI, BigQuery, GCP Buckets) — available
D5: Security Review PCI-DSS — InfoSec — in progress
D6: Legal/Contract review for merchant AI data agreements — Legal — [Needs Decision: addendum vs new contract]
D7: Risk Review Wave #224847 — Governance — submitted, ~2 month timeline

### Core Hypotheses
H1: Merchants need agents that complete work, not just surface insights [validating in Alpha]
H2: Platform-embedded agents outperform standalone AI assistants [validating in Alpha]
H3: Merchants will delegate tasks with appropriate trust thresholds [Gap: thresholds undefined]
H4: Time saved translates to growth activities and satisfaction [Gap: measurement methodology needed]
Fallback: even if merchants delegate less than expected, platform still has value as shared infrastructure. Worst case = slower ramp to autonomous execution, not failed platform.

### Competitive Landscape
Toast IQ: validates insight-to-execution model. GPN advantage: accuracy/governance gaps, limited user permissions.
DigitalGenius: validates autonomous resolution. GPN advantage: they are customer service only, limited scope.
Shopify Sidekick: validates platform-centric assistant model. GPN advantage: limited cross-system orchestration, retail-only.
Intuit QuickBooks: multiple task-specific agents. GPN advantage: siloed agents, no unified control plane.
Google UCP: structural enabler. GPN advantage: no merchant domain expertise.

GPN differentiation: unified orchestration, trust and governance model, cross-vertical coverage, proprietary payment data unavailable to pure software competitors.

## Essence
A full PRD capturing the merchant problem (app fatigue + admin burden), platform problem (duplicate AI builds across GPN), user personas, functional and non-functional requirements, phased success metrics, known measurement gaps, platform dependencies, core hypotheses, and competitive positioning. The through-line: agents that execute, not just inform, built on a shared governed platform.

## Interesting Because
The measurement gaps section is unusually honest for a PRD. Flagging that the 60% admin reduction claim has no methodology yet, that pricing is undefined, that task completion has no definition — that is either a sign of unusual intellectual honesty or a sign that there are some important conversations still to be had before Beta. Either way it is the most important section in the document.

The hypothesis fallback is also worth noting: "worst case is a slower ramp to autonomous execution, not a failed platform." That is a really good way to frame downside risk to an exec audience.

# gate-diff calibration — tool inventory over gstack's last 50 merged PRs

Generated by `bun scripts/gate-diff-calibrate.ts --ref origin/main --count 50 --markdown`
on 2026-10-10 against `origin/main` at `20eb620` (v1.91.68.0), scanning each
commit's first-parent delta exactly as `gstack-gate-diff --commit <sha>` does.
gstack squash-merges, so the 50 first-parent commits are the 50 landed PRs.
The clone was shallow; `git fetch --deepen=60 origin main` was needed first
(the tool reports a missing parent as `GATE_ERROR=no_base … fix=git fetch --deepen`).

## What this measures, and what it does not

This is the **tool's inventory**: how many hunks the floor lists per PR, how
many are eligible for the read level, how often the 50-hunk / 200 KB read cap
makes a result partial, and how often each tag fires. Tags are factual labels
(a test deleted beside its deleted source is still RH-1), so a tag count is not
a count of problems.

It does **not** measure agent findings, kept/restored/open dispositions, or
whether a reviewer would have wanted to read a tagged hunk. The design's
10-PR hand read of tagged hunks is a human step this table only supports; the
agent-level signal is collected after ship from the persisted review records.
No artifact was written: calibration never touches the state root.

## Observations from the numbers

- **Listed per PR:** median 40.5, p75 267, max 1,276 (the v1.91.8.0 test-audit
  wave); eligible median 31.5. This matches the design's own measurement
  (median 23–45) and confirms per-hunk disposition is unworkable; the three
  levels are the right unit.
- **Partial results:** the read cap was hit in 20 of 50 PRs. For gstack's
  test-heavy PRs, "partial (K of M eligible read)" will be the common state,
  not the exception.
- **RH-15 (paired, 35 hunks / 14 PRs)** reads well by inspection: real
  `timeout-minutes` bumps in workflows, `timeout 5000 -> 30000` in tests, a
  judge threshold `4 -> 3`, an exact-count assertion relaxed to a bound, plus
  tightenings labelled as such. The direction note makes the read fast.
- **RH-15? (unpaired, 848 hunks / 41 PRs)** is dominated by `spawnSync(…,
  { timeout: 30_000 })` in new or moved test code; this repository requires a
  timeout on every synchronous spawn (`test/spawnsync-timeout-tripwire.test.ts`),
  so nearly every test PR carries dozens. As specified ("unpaired values are
  tagged RH-15? and read") the tag is noise here. **Decision (integrator, per
  the design's demotion rule):** `RH-15?` now applies only to CI and
  runner/lint-config files; in test files unpaired values are inventory and
  only paired RH-15 is tagged. The table below predates that change. The detector was
  tightened to key-value assignments (`key: N`, `key = N`, `key(N)`, `--key N`,
  and a gate key opening a nested structure) and to numeric literals with `_`
  separators; prose strings and `setTimeout` calls no longer fire.
- **RH-1 (411 hunks / 18 PRs):** 343 of them are the v1.91.8.0 test-retirement
  PR; 29 are skip/only idioms (several are conditional
  `process.platform === 'linux' ? describe : describe.skip`). Factual, and
  exactly the inventory a reviewer of that PR would want listed.
- **RH-16 (80 hunks / 19 PRs):** gstack's many best-effort `catch {}` blocks.
  Overlaps slop-scan as the design states; listed under the RH id.
- **RH-12, RH-13, RH-14:** rare (6 / 8 / 3 hunks), plausible on inspection.
- **RH-3 / RH-3?:** did not fire; gstack has no `__snapshots__`/`.golden`
  fixtures in this window (its SKILL.md goldens are `.md`, listed by path only).
- Prose (`.md`, `.md.tmpl`) and generated/vendored paths (`dist/`, `vendor/`,
  lockfiles, `.min.js`) are floor inventory only; without that rule the
  design document itself tagged every RH id it describes.

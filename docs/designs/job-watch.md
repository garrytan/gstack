# Design: Job Watch

Generated by /office-hours on 2026-09-01
Branch: main
Repo: garrytan/gstack
Status: APPROVED
Mode: Startup

## Problem Statement
Founder is actively job-searching and manually re-checks 2-3 job portals
near-daily (~10-15 min/session, ~70-100+ min/week) hunting for postings
they haven't already seen. Job Watch: set a role + location, hit "Check
now," get back current postings with anything unseen marked "New." State
persists between checks so old postings stop being re-flagged.

## Demand Evidence
First-person, present-tense: founder is job-searching right now, not
hypothetically. Quantified status quo cost: 2-3 sites, near-daily,
~10-15 min/session (~70-100+ min/week). Real stakes, externally verified
via web search (not just founder intuition): early applicants get
roughly 3x higher interview odds, and a competitive role can receive
200+ applications within the first 24 hours — missing a posting by a day
or two can mean missing the early-applicant window entirely.

## Status Quo
Manual re-scanning of 2-3 job portals near-daily. Founder has actually
tried LinkedIn/Indeed-style job alerts (not just assumed they'd fail) and
identified a specific, tested failure mode: those alerts are delayed or
batched (daily/weekly digest), not real-time — by the time the alert
arrives, the early-applicant advantage may already be gone.

## Target User & Narrowest Wedge
The founder, currently job-searching. Narrowest wedge: a single tracked
role + location search, diffed against previously-seen postings on manual
demand — not a job aggregator, not a matching/relevance engine.

## Constraints
- Founder has genuinely tested the alternative (existing job alerts) and
  hit a specific failure (delay/batching), not an assumption.
- Landscape research: existing job-alert tools mostly fail via a
  *different* failure mode — over-broad keyword/AI matching creates a
  "fire hose not funnel" of noisy, irrelevant postings, which drives
  people back to manual checking despite having alerts configured. Even
  sophisticated AI-matching tools don't fully replace manual checking —
  "most people use two or three apps together" (industry sources).
- v1 deliberately does not attempt relevance/matching — it only diffs a
  single fixed search against its own prior state. This sidesteps the
  noise failure mode by design, not by being smarter about relevance.
- Scraping job portals directly carries real risk that the original
  session underweighted: JS-heavy rendering, anti-bot/rate-limiting, and
  ToS restrictions (e.g. LinkedIn actively pursues scrapers). Caught in
  spec review — see Data Source below for the resolution.

## Premises
1. Real, present-tense, first-person demand exists (founder is
   job-searching now, checking 2-3 sites near-daily, ~70-100 min/week) —
   AGREED.
2. The stakes are real and externally verified (early applicants get
   ~3x higher interview odds; competitive roles hit 200+ applications
   within 24h) — AGREED.
3. This is genuinely different from existing job alerts — the founder's
   tested failure mode is delay/batching, and a narrow diff-only tool
   avoids the noise problem that broad AI-matching tools suffer from —
   AGREED.
4. Feature 1 is a manual on-demand diff, not automated polling — REVISED
   during the session. Originally framed as "manual is fine, I'll check
   more often than alerts do." The second opinion challenged this
   directly: manual-only doesn't fix the founder's own stated pain
   (timing/delay) — it relocates the delay-risk from "the tool's batch
   interval" to "however often the founder remembers to click a button,"
   which is a personal-discipline bet, not a structural fix, and
   discipline tends to decay as a job search drags into its second and
   third week. Revised premise: manual-only is an UNPROVEN bet, not a
   solved problem. Check-frequency gets instrumented from day 1 (see
   Success Criteria) so the bet is measured, not assumed. If check
   frequency decays over the first 2 weeks, automatic polling + a
   notification fallback is the real v2 — not a someday-maybe.

## Cross-Model Perspective
Independent Claude subagent cold read (Codex unavailable on this
machine):

- **Steelman:** a "diff engine" for a single saved search — not an
  aggregator, not a matching algorithm, just a trustworthy delta
  detector. It wins by refusing to do relevance judgment at all, which is
  exactly what every competitor gets wrong and exactly what makes them
  noisy.
- **The tell:** "tell me what changed since I last looked at this ONE
  fixed search" — a diff problem, not a matching problem. The entire
  feature surface is fetch → compare against last-seen state → mark new
  → persist. No ranking, no ML, no multi-source merging. Every future
  feature request that adds relevance/matching logic is scope creep away
  from the one thing that's actually defensible.
- **Premise challenged:** disagreed with the original framing of premise
  #4 ("manual is fine") — see Premises above for the full argument and
  the resolution (instrument check-frequency, treat manual-only as
  unproven).
- **48-hour prototype (original subagent framing — refined in spec
  review, see Data Source and Approach A below):** single script + flat
  JSON (one user, no DB server, no deployment). One fetcher for exactly
  ONE job source. A normalized posting ID with first-seen timestamp.
  Diff-on-click: fetch, compare IDs, mark unseen as "New," persist. Skip:
  auth, scheduling/cron/polling (the v2 fallback), notifications,
  multi-site aggregation, relevance logic. Log every "Check now"
  timestamp to a file from day one — the only way to actually test the
  check-frequency bet instead of assuming it. Spec review resolved the
  originally-open "which source, scraped how" question by identifying an
  available Indeed MCP tool as the data source, removing the scraping
  risk this framing hadn't accounted for.

Founder revised premise #4 to accept the critique rather than defend the
original framing — chose to measure the bet instead of assert it.

## Data Source (resolved in spec review)
This environment has an Indeed job-search MCP tool available
(`search_jobs`: title/keywords + location + country code → structured
results with apply links; `get_job_details`: job ID → full description) —
no auth step, sourced from Indeed's own job search API. This is strictly
better than a bespoke scraper for v1: no ToS risk, no JS-rendering risk,
no anti-bot risk, and it directly returns structured data instead of HTML
to parse. **Job Watch v1 uses this Indeed MCP tool as its data source
instead of scraping**, which removes Approach A's biggest hidden
feasibility risk. Approach C (reusing gstack's browse infra for
scraping) is no longer needed for v1 as a result — only reconsider
scraping if a source outside Indeed's coverage becomes necessary later.

**How "Check now" actually reaches the MCP tool (resolved in second spec
review pass):** MCP tools are exposed to an agent session, not to an
arbitrary standalone HTTP server process — a plain Node server has no
built-in path to call `search_jobs`. For v1, "Check now" is implemented
as a short script invoked through the Claude Agent SDK (or `claude -p`
as a subprocess) with the Indeed MCP server configured for that
invocation. This is a normal pattern for a personal tool built by a
Claude Code user and doesn't require any separate Indeed API key or
credential. Tradeoff worth naming: each "Check now" click costs one
agent-turn's latency/cost instead of a raw HTTP call — acceptable for a
manual, on-demand v1, but a reason NOT to add automatic polling on top
of this exact mechanism without reconsidering the invocation path first.

**Parsing (resolved in eng review — verified live, not assumed):** a
live probe of `search_jobs` confirms it returns a fixed, consistent
markdown template per job — `**Job Title:** ... **Job Id:** JOBSEARCH_98
**Company:** ... **Posted on:** ... **View Job URL:** ...`, repeated per
result. Because the format is stable, **the agent-turn's only job is to
invoke the tool and return its raw text — all field extraction
(job_id, title, company, posted date) is a deterministic regex parser
in the server code, not something the LLM re-interprets on every call.**
This matters for correctness, not just cleanliness: the diff mechanism's
entire job is comparing `job_id` across checks, and an LLM asked to
"extract and reformat as JSON" isn't guaranteed byte-identical output
between calls — a mistranscribed job_id would silently break the diff
(false "New," or a genuinely new posting never flagged). A regex parser
against a stable template has no such risk.

**Failure layering (resolved in eng review):** there are two distinct
failure layers, and they need distinct user-facing messages, not one
generic "check failed":
1. **Agent-invocation layer** (Claude auth expired, network down,
   rate-limited/quota exceeded) — the agent-turn never gets far enough
   to call `search_jobs` at all. Show: "Job Watch can't reach Claude —
   check your login" (or similar, naming the actual layer that broke).
2. **Tool-call layer** (`search_jobs` itself errors, e.g. Indeed's
   backend is down) — the agent-turn ran fine but the tool call failed.
   Show: "check failed, try again" (the existing message below).
Distinguishing these means a 7am failure tells you WHICH thing broke
(your Claude session vs. Indeed's API vs. your network) instead of
leaving you debugging blind.

## Approaches Considered
### Approach A: Minimal Diff Tool (chosen)
A single served local webpage (not a bare CLI script — the founder chose
"simple local webpage" for the Check-now interaction) backed by a small
Node/TypeScript server. Role + location are set via a form field on that
page (not a config file or CLI arg — keeps the founder's stated UI choice
consistent end to end). "Check now" calls the Indeed `search_jobs` MCP
tool for the tracked role + location, diffs the returned postings against
locally stored state, and marks unseen ones "New."

**Data flow (added in eng review):**
```
[webpage: role/location/countryCode form + "Check now" button]
              │ POST /check
              ▼
[thin Node/TS server]
              │ spawn agent-turn (claude -p / Agent SDK,
              │ Indeed MCP connector configured)
              ▼
        ┌─────┴─────┐
   FAILS│           │succeeds
 (auth/network/      ▼
  quota — layer 1) [search_jobs MCP tool call]
        │            │
        │       ┌────┴────┐
        │  FAILS│         │succeeds
        │ (Indeed backend │
        │  down — layer 2)▼
        │       │   [raw markdown text returned
        │       │    to server, fixed template]
        │       │         │
        │       │         ▼
        │       │   [server: regex parser extracts
        │       │    job_id/title/company/postedAt
        │       │    — deterministic, no LLM]
        │       │         │
        │       │         ▼
        │       │   [diff against seenPostings by job_id]
        │       │         │
        │       │         ▼
        │       │   [update seenPostings + append
        │       │    checkLog entry, write JSON]
        │       │         │
        ▼       ▼         ▼
  "Can't reach   "check      [return postings + New
   Claude —      failed,      flags to webpage]
   check login"  try again"
```
State (`seenPostings`, `checkLog`) is untouched on either failure path —
only a successful parse+diff mutates the JSON file.

**Storage (committed, not left open):** flat JSON file — one user, one
tracked search, no need for SQLite's overhead. Schema:
`{ trackedSearch: {role, location, countryCode}, seenPostings: {[postingId]: firstSeenAt}, checkLog: [{timestamp, newCount}] }`
— `countryCode` is required because `search_jobs` requires it; the form
field defaults to "US" but is editable.

**Storage edge cases (added — eng review):** file missing (very first
run ever) → initialize an empty structure silently, this is the
expected first-run state. File exists but is corrupted/invalid JSON
(e.g. a crash mid-write) → show a distinct error and refuse to proceed,
never silently treat corruption as "empty" — that would wipe
`seenPostings` history and re-flag every current posting as "New" on
the next check, which is exactly the false-signal failure mode the
whole tool exists to avoid. Writes should be atomic (write to a temp
file, then rename) so a crash mid-write can't produce a half-written,
corrupted file in the first place.

**Posting-ID / dedup rule (committed, not left open):** Indeed's job
results carry a stable `job_id` (used by `get_job_details`) — use that
directly as the posting ID. This sidesteps the URL-normalization problem
(tracking params, session tokens) that a scraped source would have
created, since `job_id` doesn't change between fetches of the same
posting. Verified live during eng review (see Data Source) — the actual
field is `**Job Id:** JOBSEARCH_98`-style, present on every result.

**First-check baseline behavior (added — eng review):** on the first
check of a new tracked search, `seenPostings` is empty. Rather than
naively marking every returned posting "New" (technically correct but
useless — a fresh search shouldn't dump 10 "New" badges on you), the
first check establishes a baseline: all current postings are shown and
recorded in `seenPostings`, but none are flagged "New." "New" means
"appeared since you last looked," not "exists" — only checks after the
first one can produce "New" flags.

**Failure handling (added — was missing; two-layer distinction added in
eng review, see Data Source):** if either the agent-invocation layer or
the `search_jobs` tool-call layer fails, log the failure, leave
`seenPostings` state untouched, and show the layer-appropriate message
(see Data Source) — never let a failed check wipe prior state or
mass-flag everything "New."

**Check-frequency log (schema committed, was unspecified):** every
"Check now" click appends `{timestamp, newCount}` to `checkLog` in the
same JSON file — this is the instrument for premise #4 (see Success
Criteria).

**Double-click guard (added — eng review):** the "Check now" button is
disabled from click until the response returns. A double-click racing
two checks would double-log one check in `checkLog`, inflating the
check-frequency metric that's the entire instrument for validating
premise #4 — measuring your own discipline wrong defeats the point of
measuring it. Disabling in-flight prevents the race outright rather than
detecting it after the fact.

**Known limitation, accepted for v1 (eng review):** `seenPostings`
entries are never removed for postings that stop appearing in results
(filled/delisted). The file grows unboundedly across a job search that
could run months — functionally harmless at this scale (a few hundred
KB at most), and building cleanup logic now solves a problem that
doesn't exist yet. Stated explicitly here as an accepted limitation, not
a silent gap.

- Effort: human ~1 weekend / CC ~1-2 hours
- Risk: Low (further reduced by using the Indeed MCP tool instead of
  scraping)
- Pros: Proves the diff mechanism and the check-frequency bet
  simultaneously; smallest possible surface to get real signal; no
  scraping fragility.
- Cons: Doesn't fix timing if the discipline bet fails — that's the
  point, it's designed to reveal that quickly rather than assume it away.
  Scoped to Indeed's coverage only for v1 — a source outside Indeed isn't
  covered without the deferred Approach C.
- Reuses: the Indeed MCP tool already available in this environment; no
  dependency on gstack's browse infra needed for v1.

### Approach B: Multi-source + auto-polling (rejected for now)
Several job boards/company pages, scheduled polling with a pre-built
notification fallback, more robust dedup.
- Rejected: skips validating the diff mechanism first, and pre-builds
  the exact automation premise #4 was just downgraded from assuming was
  necessary. Revisit only if Approach A's check-frequency log shows
  decay.

### Approach C: Reuse gstack's browse infra (considered, not chosen for v1)
Same minimal scope as Approach A, built on gstack's existing headless-
browser scraping ($B binary) instead of bespoke fetch/parse logic — useful
since job portals often lack clean RSS/APIs.
- Not chosen for v1: adds a dependency on gstack's infra to a project
  that's explicitly separate from gstack; worth reconsidering later if
  the chosen job source turns out to need real browser rendering (JS-
  heavy listing pages) rather than a simple HTTP fetch/parse.

## Recommended Approach
**Approach A: Minimal Diff Tool**, chosen by the founder. One source, one
tracked search, manual check via a simple local webpage, check-frequency
instrumentation from day 1.

## Open Questions
- Does check frequency hold or decay over the first 2 weeks of real use?
  This is the load-bearing open question — it determines whether v2 is
  "polish the diff tool" or "add automatic polling + notifications."
- If a job outside Indeed's coverage matters enough to track, revisit
  scraping (and gstack's browse infra) then — not for v1.

## Success Criteria
Approach A: the diff mechanism correctly marks only genuinely-unseen
postings as "New" (no re-flagging of previously-seen postings). The real
test is the check-frequency log: if the gap between consecutive "Check
now" clicks holds steady or shrinks over the first 2 weeks of real use,
premise #4 (manual-only) is validated. If the gap grows, the manual bet
is failing and automatic polling + notifications become the actual v2.

## Distribution Plan
Not applicable at this stage — Approach A runs locally, no deployment,
single user (the founder).

## Dependencies
Not "none" — the real dependency (named explicitly per eng review) is a
**working Claude Code / Agent SDK session with the Indeed MCP connector
enabled, present at the moment of every "Check now" click.** This isn't
a standalone webapp that runs anywhere: it can't be deployed to a bare
VPS or a plain cron job without that agent runtime present. That's an
acceptable tradeoff for a personal tool run from your own machine, but
it rules out "set it and forget it on a $5 server" as a v1 option — the
checking machine needs an authenticated Claude session every time.
Approach A can otherwise start today — the source-selection question
that previously blocked Day 1 is resolved (Indeed, via the MCP tool).

(`{timestamp, newCount}`) to the same file from the very first use — that
log is what tells you in 2 weeks whether the core bet (manual checking
beats batched alerts) is actually working, instead of just hoping it is.

- **A Capy install run inside an open /ship or review no longer upgrades gstack under it.** During a /ship on gstack-evals #252, the docs audit's session check ran `install.sh --for <skill>` and moved gstack from 1.96.0.0 to 1.97.0.0 mid-run: the workflow lease that was meant to stop it only counts for 120 minutes, and a long /ship outlives it. The Capy session now also looks for a run that is still open on this machine's state root: a /ship budget ledger with no `closed_at` that was written in the last 6 hours, or a review start that `gstack-review-log --finish` has not consumed and that is under 120 minutes old. While one is open the session keeps the installed gstack, prints `SELF_UPGRADE: deferred (...)` naming the run, and still ends `gstack: ok <installed version>`; once the ledger closes, the next install upgrades as before. Below the supported minimum nothing changes, and the floor still refuses or fast-forwards. (GST-1677)
- **Smaller fixes on the same upgrade path.** The eval-lock probe now works without the `flock` binary (python3 or perl stand in, as on macOS). When an unreasoned pin is overridden, the session takes the setup lock before it switches branches and hands it to `gstack-upgrade`, so no other updater sees the checkout between the switch and the fast-forward; an older `gstack-upgrade` on the local default branch, which cannot take the lock over, gets it released and takes it itself, so it still upgrades. A default branch the override creates now tracks origin. A failed restore after a refused fast-forward says `pin not restored` with the command that puts HEAD back, instead of claiming the pin was kept. The no-fetch stale check reads file times with `stat` instead of GNU-only `date -r`. A pin reason can no longer add its own `fix:` note to the trailer, and a reason with nothing pinned is not reported as a pin. The no-fetch fix note names the install command even when the bootstrapper's path is unknown. (GST-1658)

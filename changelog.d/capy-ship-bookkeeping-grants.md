**/ship stops asking owners for grants around its own bookkeeping.**

### Fixed
- **A round grant now buys the round its `PR_ROUND_CAP` stop names.** When a pull request past its two review rounds got a read-only final review that found a blocker, the lane's round grant at that head raised the cap by one, but the read-only pass already counted as that round, so the next run was read-only again and no fix round opened (gstack#4272 needed a new PR; ghome#17 needed a second grant). `gstack-ship-receipt stub` now marks a run that started past the cap `read_only`, the mark survives that run's receipt write and its fix commits, and once a grant applies, `history` leaves those passes out of `--prior-full`. The granted round also keeps its fix round (its pass 2), and nothing past it plans. A grant now also applies across a base merge that leaves the PR's own added and removed lines byte-identical and in the same places, since preflight merges the base before the review; a head that changes or moves those lines, or a base edit right next to them, still needs a new grant. See docs/review-policy.md#rounds-per-pull-request.

- **A base merge that only touched base-side text no longer stops `/ship` finish for an owner's grant.** After a main merge, finish counted two base-side differences as "behavior, tests or build inputs changed since review": the shared-preamble hash id in every regenerated skill file the branch also touched (#4383, 94 files), and an expected-value list where main's new entry was spliced next to the branch's own (ghome#16). The path comparison now reads both sides with the shared-preamble ids masked (a file whose only branch change is that id compares as unchanged), and a line that is the base's new line plus exactly the tokens the branch added to the reviewed line counts as base context, so it goes to the one scoped reader instead. A resolution that drops, invents or rewrites anything on the branch's own lines still stops as a behavior change.

- **A reviewer's confirmation prose no longer becomes a Critical finding that only an owner can clear.** The collector read prose that named a file and line while confirming code, such as "a High or Critical challenge…", as an anchored Critical finding that judgment could not lower, even when the reply's own `REVIEW_VERDICT` said `blocking=0` or it said `NO FINDINGS`, so each one cost an owner ruling and a stopped `/ship` (twice on #4431). A file:line in prose, or a list item or the native voice's FIXABLE tag in a reply that says `NO FINDINGS`, no longer anchors a finding, so under a `blocking=0` verdict such a row is a summary candidate the lead can lower with a reason. It still blocks until then, so prose that names a real blocker ("no Critical issues except the token leak in log.ts:3") is never dropped. Structured findings (JSON, a lead severity label, a label heading, a numbered finding heading, a `Severity` or `Blocks: yes` field, or the native voice's FIXABLE/INVESTIGATE tag) still collect as anchored and still disagree with the verdict, and a reply whose verdict declares a blocker is read as before.

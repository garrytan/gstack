- **gstack stops draining the shared GitHub GraphQL quota.** `gstack-pr-wait` read the pull request through a GraphQL query and `gh pr checks` every 20 seconds (as often as every 5), about 360 GraphQL calls an hour per watcher, and the Capy app installation's 7,700-point hourly budget ran out right after each reset, stalling merges across crews. It now reads the PR state, base head and head-commit checks from REST, and makes its one GraphQL read (comments, reviews and review-thread resolution) only when the PR changed, every 10 minutes, or once green under `--until ready`. Every gstack wait between GitHub reads now goes through `lib/gh-poll.ts`, which puts a 60-second floor plus up to 15 seconds of jitter under it: `gstack-pr-wait` (was 20 s), `gstack-ci-gate --wait` and its registration re-poll (were 30 s and 10 s), `gstack-ci-carry wait` (was 20 s), `gstack-ship-release accept` (was 15 s), `gstack-greptile-early wait` (was 30 s, and its head read moved to REST), the merge-train and land waits (were 30 s, and 3 s for land's merge readback) and eval-bg's run follow (was 10 to 30 s). A gh call that fails with a rate-limit message is no longer retried at once. The gh runners read `gh api rate_limit`, sleep until that budget resets (at least 60 s) and retry at most twice. The one exception is `gh pr merge`, which runs under the land lock and still fails at once. `test/gh-poll-tripwire.test.ts` fails on any new wait in a GitHub-reading module that skips the floor. (GST-1713)

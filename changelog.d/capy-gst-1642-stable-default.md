- **New installs follow the stable channel; Capy crews stay on main.** A fresh `git clone … && ./setup` now records `update_channel: stable` the first time it runs on a machine and prints `Update channel: stable (new install)` with the command that switches, so a new user gets the twice-weekly tested release instead of every merge to main (the clone starts at main's tip and joins releases at the next cut that passes it). A gstack contributor's checkout (`bin/dev-setup`'s marker, another branch, local commits, CI) still follows main, and every install set up before this change keeps following main: nothing switches under anyone. Capy crew machines stay on main: `bin/gstack-capy-session` pins `GSTACK_UPDATE_CHANNEL=main` unless the variable names a channel, a fresh Capy machine records main, and the Capy skill bootstrapper (wrapper 5) no longer follows a machine's own channel. The README install section says which channel you get and how to switch. (GST-1642)
- **Capy threads run gstack's latest main at least daily.** When the oldest origin commit a Capy checkout lacks is more than 24 hours old, the session check's trailer says `stale=<h>h` and the skill runs the install before the next workflow. A pin (`GSTACK_CAPY_SELF_UPGRADE=off`, `GSTACK_CAPY_AUTO_UPGRADE=0`, a detached HEAD or another branch) holds past that only with a recorded reason (`GSTACK_PIN_REASON`, `git config gstack.pinReason`, an explicit `--revision`); an unreasoned one is overridden at the workflow boundary and reported (`PIN_UNREASONED`). The upgrade never runs under a live workflow lease or eval run, never switches a checkout another session holds or onto diverged work, and a failed fetch with none successful in 24 hours is reported. (R75, GST-1642)
